# S3 ENGINE: contract proposals

Every item below already has a backward-compatible local workaround in `engine/server`. The drift test stays green, and nothing here blocks integration.

## P1. Optional hooks on `fvwks_voice.api` (seam additions)
The server looks these up with `getattr`. When a hook is missing, it falls back to the v0 stub behaviour. The exact signatures went to S1 on 2026-09-26, after the coordinator approved model downloads. S1 already ships `warm_up()`.

| Hook | Used by | Fallback today |
|---|---|---|
| `ENGINE_VERSION: str` | Salts the TTS and stack caches, so a new model or voice build misses old entries | `ENGINE_NAME` only |
| `warm_up() -> None` | `fvwks-engine` start-up. `/api/health` reports `loading_model` until it returns (not run under TestClient). | Engine is `ready` at once |
| `configure(data_dir: Path) -> None` | Called once at start-up with `<data dir>/voice`, which the voice package owns (persona clips and metadata) | Nothing |
| `list_models() -> list[ModelInfo]` | `GET /api/models` (real `installed` and `size_bytes`) | Static Kokoro and Qwen3 list |
| `install_model(model_id: str, progress: Callable[[float \| None, str \| None], None]) -> None` | `POST /api/models/{id}/install`: a background job in the `install` lane, one download at a time, deduped per model. The server first checks that free space ≥ `size_bytes` + 5 GB; if not, the job fails with `disk_full` and a hint. `progress()` raises when the user cancels, and the installer must let that propagate. `ENOSPC` during the download also becomes `disk_full`. | Job error `not_available` |
| `design_persona(req: PersonaDesignRequest) -> list[Source]` | `POST /api/personas/design`. The server stores each candidate and returns the candidate audio ids in `Job.result_ids`. | Job error `model_missing` |
| `save_persona(name: str, candidate: Source) -> Voice` | `POST /api/personas`. The voice package owns persona storage and lists the persona in `list_voices()`; the server dedupes by id. | 404 for the candidate |

Errors raised by any hook that carry `code`, `message`, `hint` and `status` (S1's `VoiceError`) become the HTTP error unchanged.

## P2. `ExportResult.warnings: list[str] = []`
`POST /api/exports` with `stems: true` exports the stems only if fx produced them. The v0 fx stub never does, and today the stems are skipped silently (the engine log records it). A `warnings` list would let the UI say "no stems: the sound engine doesn't produce them yet".

## P3. Document the preset-hint rule (behaviour, no schema change)
The server fills every `None` field of a `RenderRequest` from the preset. It also applies `Preset.arrange_hint` and `master_hint` to exactly the `Arrange` and `Master` fields the client **did not send**. For example, GHOST's `first_word_beat: 4` applies unless the request sets `arrange.first_word_beat`.

For S4: send only the fields the user actually changed. A full `Arrange` object would override the preset's hints.

## P4. `SourceInfo.analysis_state` (nice to have)
WORLD analysis runs in a background job after every new source (`fx.analyze`). The engine tracks its state (`none|queued|running|done|error`), but the contract doesn't expose it. The UI could show "analysing…" before the first preview.

## P5. `Health.missing_models: list[str] = []` (first-run readiness): adopted in v0.4 as `Health.required_missing`
On a fresh Mac, the engine installs the required models (Kokoro, deepfilternet3) on first launch through the ordinary install jobs. Meanwhile `/api/health` reports `loading_model`, with the overall download progress and the installer's message ("Downloading Kokoro 82M: 0.1 of 0.4 GB"). Opt-in models are never installed on their own.

What's missing is a structured way to say which required models are still absent afterwards. For example, the denoiser's download failed but TTS works: the app is `ready`, but recordings aren't cleaned. Proposed, additive with a default:

```python
class Health(Model):
    ...
    missing_models: list[str] = Field(default_factory=list,
        description="Ids of required models that aren't installed (GET /api/models has the details).")
```

- **What the app can do with it:** show a "finish setup" action next to the status, with a retry via `POST /api/models/{id}/install`, without parsing the message.
- **Workaround today (no schema change):**
  - `Health.message` reads "Not installed: DeepFilterNet3 denoiser (VOICES → Models)." while the engine is `ready`.
  - If Kokoro itself fails to download, the state is `error`, and the message is the download's own error and hint (network, disk).
  - `GET /api/models` already has `required` and `installed` per model.

## P6. `ModelInfo.install_job_id` and `ModelInfo.install_needs_bytes` (model screens): adopted in v0.5
Two additive fields on `GET /api/models`, both defaulting to `None`:

```python
class ModelInfo(Model):
    ...
    install_job_id: str | None = Field(default=None,
        description="The model's install job while it is queued or running (GET /api/jobs/{id} for progress).")
    install_needs_bytes: int | None = Field(default=None,
        description="Free disk space the install needs now: what is left to download plus the 5 GB reserve.")
```

- **`install_job_id`:** S4's model cards keep install job ids only in renderer memory (`useUi.installJobs`).
  - After a reload or an engine restart, a card loses its download and shows "job_lost".
  - A card can't show the downloads the engine starts by itself on first launch (P5).
  - With this field, every card reattaches to whatever job is running.
- **`install_needs_bytes`:** the card hardcodes the engine's 5 GB reserve, and assumes the full `size_bytes` must still be downloaded. The engine's own guard counts what's left, since a resumed download needs less. This field makes the card's "needs X GB free" match the engine's decision exactly.
- **Workaround today:** `POST /api/models/{id}/install` is idempotent while an install is active; it returns the same job (dedupe per model). A card that lost its job can re-POST for a model the user is installing.

## P7. `ApiError.model_id: str | None = None` (deep link to the missing model): adopted in v0.6
A `model_not_installed` (503) error would name the model, so the app's "Install" link can call `openModelsFor(model_id)` without parsing the message (S4's ask).
- S1's `VoiceError` gets an optional `model_id` attribute.
- The server's passthrough copies it, as it already does `code`, `hint` and `status`.
- **Workaround today:** the hint names the model in words.

## P8. `DELETE /api/models/{model_id}` → `ModelInfo`: adopted in v0.6
Frees disk from the Settings → Models section.
- **Errors:** 409 `model_required` for required models; 409 `model_busy` while the model is installing or loaded (e.g. the persona model during a design).
- **Needs:** an S1 hook, `uninstall_model(model_id)`, which removes that model's cached repos.

## P9. Model updates through a small versioned manifest: adopted in v0.6 (`SignedModelManifest`)
- **Manifest:** published next to app releases:

  ```json
  {"schema": 1, "published": "2026-10-01",
   "models": {"kokoro-82m": {"version": "1.1", "notes": "Clearer consonants.",
                             "repos": [{"repo_id": "mlx-community/Kokoro-82M-bf16", "revision": "<commit sha>",
                                        "size_bytes": 356398294}]}}}
  ```
- **Who fetches it:** the app shell, which already checks for app updates. It fetches one feed, only when the user allows it ("Check automatically" or CHECK NOW), and hands the models part to the engine through `PUT /api/models/manifest`. The engine itself never goes online to check.
- **Verification:** the engine checks the manifest's ed25519 signature against a public key built into the app.
- **What it changes:** `GET /api/models` then shows `version` and `update_available`. `POST /api/models/{id}/install` downloads the manifest's revision; the model stays usable until the new one is complete, then swaps.
- **S1's conditions:**
  - A manifest may only move pins to revisions with the same file names and license. The loaders pass `model_type` explicitly, and Kokoro voices are read by file name. Anything else needs a new engine build.
  - The disk guard stays in place (remaining download + 5 GB).
- **Why pinned revisions:** Hugging Face commit shas are content-addressed, so a revision always means the same bytes, and the download verifies each file against it.

## P10. Sample packs: "drop a folder of one-shots" (M3.9, 1.5.1)

The engine half exists: `fvwks_synth.oneshots.scan(folder)` finds a folder's drum one-shots and names each one's role (kick, snare, clap, hat, open_hat, cymbal, reverse, impact, perc), and `fvwks_synth.layers` layers them under the synth kit. This proposal lets the app add a pack.

**Paths.** This follows the Rekordbox import's precedent: the engine reads the user's own files where they are, copies nothing, and never returns or logs a path.
- The difference is that a folder can't be uploaded. So the **main process** (never the renderer) sends the folder path the user picked in the OS folder dialog, and only in `POST /api/sample-packs`.
- The engine applies the Rekordbox gate to the folder and to every file in it:
  - local paths only, with symlinks resolved and then re-checked;
  - regular files only, with an audio-extension allowlist (wav, aif/aiff, flac, mp3);
  - at most 20 MB and 2.2 s per file, the length read from the header first;
  - at most 5,000 files a pack.
- The path is stored server-side (library DB) and appears in no response and no log. Packs and samples are opaque ids and names (file stems).

**Routes**
- `POST /api/sample-packs` `SamplePackAdd {folder: str, name?: str (1–80)}` → `Job` (kind `sample_scan`). The job's items are the files, done or error with `code` = `not_one_shot` | `unreadable` | `unsupported`; `result_ids` = [pack id]. It returns 400 `not_a_folder` and 404 `missing`.
- `GET /api/sample-packs` → `[SamplePack {id, name, created_at, available: bool (the folder is still there; a drive may be unplugged), counts: {role: n}, enabled: bool}]`.
- `GET /api/sample-packs/{id}/samples` → `[PackSample {id, name, role, confidence 0–1, seconds, preview_audio_id}]`. The preview streams through GET /api/audio/{id}, rendered on first play.
- `PATCH /api/sample-packs/{id}` `{name?, enabled?}` and `PATCH /api/sample-packs/{id}/samples/{sid}` `{role}`: the user corrects a role.
- `DELETE /api/sample-packs/{id}` → 204. It forgets the pack; it never touches the files.
- `POST /api/sample-packs/{id}/rescan` → `Job` (the same scan; the user's role corrections are kept by file).

**In the sound.** `kit.layer` (a take axis today) draws its one-shot per role from the bundled CC0 bank plus the enabled packs, seeded per take. A pack sample's clip_key includes its file's content hash, so an edited file re-prepares. Nothing else in the contract changes.
